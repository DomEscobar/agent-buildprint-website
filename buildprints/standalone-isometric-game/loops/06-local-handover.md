# Deliver the complete local game or a precise blocked state

## How to implement this loop
Read the host `AGENTS.md`, `.buildprint/next-agent.md`, approved `PROJECT_CONTRACT.md`, packet `02-identity.md` and `loops/loop-flow.md`. Resolve packet paths relative to immutable snapshots after bootstrap; host data paths are relative to the game root. Load only relevant pinned framework skills under the available tool policy. Run only authorized work, with concise progress updates and durable upstream receipts.

1. Read `HANDOVER.md` and produce the host handover with actual paths, installed package/lock identity, framework commit and archive SHA-256. Link the single approved contract and any authorized amendments; do not duplicate its requirements into another brief.
2. Link current upstream acceptance outputs and real captures/clips; identify exact tested browsers/viewports, emulation versus physical device and reviewer independence. Do not rerun unrelated checks merely to decorate the report. Any final edit invalidates affected evidence and routes back to the appropriate capture/review check.
3. Include actual host run/build commands from its package, local asset locations, source and attribution/license records, save/recovery instructions and measured/uncertain spend. Recheck no secrets, signed private URLs or provider credentials are embedded in the distributable host.
4. Name all remaining agreed content, stale/missing evidence, API/access/budget limitations and fallback quality boundaries. Distinguish implemented from verified from accepted; state no game-wide pass when an acceptance prerequisite remains open.
5. Deliver locally only unless the owner separately authorized a release. Do not push, deploy, create hosting services or claim public routes. A future release must preserve existing configuration and prove the actual published candidate separately.
6. For unfinished work, give the next eligible check/loop and concrete blocker decision, keep prior evidence, and arrange a real continuation path if promising follow-up. Do not reduce requested scope or ask again about settled approvals.

## Building objective
Deliver a maintainable standalone local game and an honest account of what the owner can trust. Preserve the full approved scope and identify exactly which requirements are implemented, functionally verified, visually accepted, motion-approved and performance-measured. The runnable host, original maps and assets, source-to-package provenance, actual entry commands and upstream acceptance evidence must travel together without secrets or misleading demo material. A package that builds is not necessarily playable, a local reviewed game is not publicly deployed, and a completed calibration is not the full agreed result. Remaining material blockers are named with concrete continuation ownership rather than hidden behind a polished handoff.

## DO NOT
Use placeholders, functionless buttons or mocked/sample data as final product or live proof. Do not copy demo/example assets/maps, edit framework internals, invent APIs or commands, spend without approval, weaken protected criteria, fake independent review, or reinterpret calibration as the full deliverable. No tests/benchmarks/browser QA/independent review during packet AUTHORING; this loop describes future authorized game work.

## Minimum proof before moving on
Actual local host/source/art locations and reproducible entry instructions; complete current evidence links or explicit unverified limits; rights/spend disclosure and precise remaining scope. Local delivery is not deployment proof. The owner receives a truthful outcome, not only a progress plan.

## Handoff note
Record the actual implemented scope, observed evidence, exact candidate/inputs, open defects and capability/authorization blockers. Link upstream production status/receipts instead of copying their verdicts. Keep current loop/next eligible work in local progress; the immutable packet index is not an auto-advancing scheduler. Preserve approvals, full scope and delegated-work ownership.
